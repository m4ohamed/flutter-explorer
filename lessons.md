# 📋 Lessons

- Ensure all variables are typed before pushing.
- When editing ARB files, preserve global metadata (`@@`) and per-key metadata (`@key`) entirely.
- Avoid side effects like re-sorting keys unless explicitly requested, to minimize diffs and preserve user formatting.
- For high-performance I/O operations (like file indexing), always use a bounded worker pool (`runConcurrent`) and batch database operations within a single transaction (`batchUpsertDartFiles`) to prevent WAL commit bottlenecks.
- **WASM Binary Bundling & Native Cleanup**: When migrating from native C++ modules (like `better-sqlite3`) to WebAssembly (like `node-sqlite3-wasm`), ensure all obsolete `rebuild`/`postinstall` scripts are removed from `package.json`. Additionally, because bundlers like `esbuild` alter `__dirname` to the output directory (`out/`), always include a build step to copy required `.wasm` binary assets to `out/` so they can be located at runtime across all IDEs (VS Code, Cursor, Antigravity).
- **Concurrent Indexing & Progress UX**: When executing concurrent tasks (like indexing multiple files with `runConcurrent`), never use the array index `i` for progress reporting, as workers finish out of order causing progress numbers to jump erratically. Always use an atomic incrementing counter (`completedCount++`), and provide immediate preliminary progress notifications (e.g. during `findFiles` or Dart SDK initialization) so the user never experiences a frozen UI.
- **better-sqlite3 ABI rebuild**: When NODE_MODULE_VERSION mismatch occurs, you MUST stop `npm run watch` first (it locks the `.node` file with EBUSY). Only after stopping the watcher can you run `npm rebuild better-sqlite3` successfully. If node-gyp fails, use `npx @mapbox/node-pre-gyp install --fallback-to-build` as a fallback.
- **flutter-explorer-mcp project path**: Always call `flutter_set_project_path` with the target Flutter project path (e.g. `E:\New folder\sad\sadara`) before any tool calls — the MCP server defaults to the wrong path (Antigravity app dir).
- **RegExp Catastrophic Backtracking (ReDoS)**: When matching nested structures like function parameters in regex, never use nested quantifiers such as `((?:[^)(]+|\([^)(]*\))*)`. On complex files or unclosed lines, this causes an exponential backtracking loop ($2^N$) that permanently freezes the Node process. Always use linear, unambiguous patterns like `([^)(]*(?:\([^)(]*\)[^)(]*)*)` to ensure O(n) matching performance.
- **SQLite WAL Multi-Process Concurrency & Lock Contention**: When accessing a SQLite WAL database across multiple Node.js processes (e.g., VS Code Extension Host as writer + MCP Server as reader) using `node-sqlite3-wasm`, you MUST explicitly pass `{ readOnly: true }` to `new Database(filename, { readOnly: true })` in the reader process. Otherwise, VFS attempts to open the database in READ/WRITE mode in both processes, instantly throwing `Failed to initialize WASM database: database is locked`. Furthermore, within concurrent worker pools (`runConcurrent`), never invoke `PRAGMA wal_checkpoint(PASSIVE)` manually after individual inserts or batch transactions. Manual checkpoints lock the database table and instantly collide with concurrent writers, throwing `SQLite3Error: database table is locked`. Always rely on SQLite's automatic WAL checkpointing (`wal_autocheckpoint`), and explicitly set `PRAGMA busy_timeout = 5000` upon connection to ensure graceful lock waiting.
- **SQLite On-Demand Connections & Retry Loop Leaks**: When implementing retry loops for SQLite connection/pragma failures across multiple Node processes on Windows, ensure that any failed `Database` instance is explicitly closed (`db.close()`) in the `catch` block. Leaving a failed connection open leaks the file handle, maintains the OS file share lock, and guarantees that all subsequent retry attempts fail. Furthermore, in long-running multi-process environments (like VS Code Extension Host + MCP Server), avoid holding permanent database connections open. Instead, adopt an On-Demand Open & Close pattern (`withDatabase`) where each read or write operation opens the database, executes the statement, and immediately closes the connection in a `finally` block. This completely eliminates cross-process file lock contention and allows retry loops to resolve collisions flawlessly.
- **Asynchronous Cache Operations & Transaction Integrity**: When refactoring caching layers (such as migrating from synchronous WASM sqlite to asynchronous native sqlite3), ensure that all consumer methods (e.g. `SqliteCache` calls in `IndexManager`) are explicitly updated to use `await`. Failing to await async methods not only causes TypeScript compilation errors (`TS2339: Property does not exist on Promise`), but also triggers race conditions where batch transactions (`batchUpsertDartFiles`) overlap with initialization (`clearAll`), leading to SQLITE_BUSY lock collisions or partial data corruption.
- **Local Package Imports & Reverse Dependencies**: In projects using package imports (e.g. `import 'package:appName/file.dart'`), do not exclude `package:` imports during index dependency analysis. Only exclude standard libraries like `dart:`. `resolveImportPath` can resolve local package imports back to relative workspace paths (`lib/file.dart`), enabling accurate reverse dependency (blast radius) calculations for the entire project.
- **Constructor Dependency Extraction (Class Filters)**: When extracting constructor dependencies, do not filter strictly by class name suffixes (e.g., `Repository`, `Service`). Instead, accept any valid Dart class naming convention and filter out known primitive/built-in Dart & Flutter types (like `String`, `Widget`, `BuildContext`, etc.). This captures all domain-specific dependencies.
- **Line-level Reference Finding**: For finding symbol references (like `flutter_find_references`), don't just rely on static file-level imports. Perform a precise regex boundary check (`\bName\b`) over the file content of importing files to retrieve exact line numbers and context snippets.
- **Re-export Blind Spot in Reference Search**: When searching for symbol references, files that use a symbol via a re-exporting intermediary file (e.g. `providers.dart` re-exports `authNotifierProvider`) will NOT appear in `usedInFiles` of the defining file's index entry. Always implement a 3-phase fallback: (1) index-based search, (2) targeted scan of `usedInFiles`, (3) full project-wide regex scan when phases 1&2 yield nothing. This guarantees 100% recall regardless of import topology.
- **Smart Import Dependency Mapping**: When matching constructor dependencies to their imports (e.g. in `flutter_get_dependencies`), don't rely only on static keyword lists. Leverage the index to resolve imports (including `package:` paths) and check if those resolved files define any of the extracted dependency classes. Fall back to name-matching and keywords to handle unindexed or third-party dependencies robustly.
- **Syncing Webview Event Handlers with HTML Structure**: When adding event listeners in a webview's JavaScript (e.g., `refreshAnalysis`), ensure that the corresponding HTML elements actually exist in the HTML template rendered by the `WebviewViewProvider` or `WebviewPanel`. If elements are missing from the HTML, JS binding fails silently, leaving tabs stale. Additionally, ensure that state changes in the core extension (e.g., `indexManager.onDidChangeIndex`) propagate relevant updates directly to the webview via `postMessage`, keeping components fresh without requiring manual tab-switching.
- **String Preprocessing vs Regex Parsing in Multi-Stage Parsers**: When designing parsers that perform string preprocessing (e.g. masking string literals or comments with spaces to avoid false positives), never run regex checks that depend on string quotes or internal string characters (e.g. `Text('hardcoded')`) directly on the preprocessed/masked text. Since the preprocessing replaces quotes and characters with spaces, the regex will fail to match. Instead, run the regex on the original source code lines and verify if the match is valid by checking if the start character at the match index in the preprocessed string is not masked (i.e. not a space).
- **State-Preserving Template Literal Masking**: When preprocessing source files in multi-stage regex parsers (such as `jsTsParser.ts`), simple replacements of template literals (backticks) can wipe out valid expressions inside `${...}` that need to be parsed. To mask template literal strings without losing code expressions, use a character scanner to find `${` blocks, trace their brace depth `{}`, and keep their contents intact while replacing all literal text characters outside the expressions with spaces. This maintains accurate line numbers, prevents false positives from string contents, and preserves valid variable/function references for usage analysis.
- **Unified Multi-Line Scope Tracking**: When parsing complex block-structured languages (like TS/JS and Dart), avoid local boolean flags for scope tracking. Implement a `ScopeFrame` stack that pushes scope entries on definition matches, tracks the brace depth (`braceDepth`) where each scope opened, and pops scopes in a central `syncBraces` function when the depth drops back. When matching multi-line headers with lookahead, pass the matched line count to `syncBraces` to process braces across all header lines at once. This avoids brace alignment issues and ensures `lineEnd` properties and usage contexts are captured perfectly.
- **vscode.workspace.findFiles Exclude Pattern**: The `exclude` parameter of `vscode.workspace.findFiles` accepts a **single GlobPattern string**, NOT a comma-separated list of patterns. To exclude multiple directories, you must use curly brace glob syntax: `'**/{node_modules,out,dist,build,.git,.next}/**'`. Writing `'**/node_modules/**,**/out/**,...'` as a plain comma-separated string will silently fail to exclude anything, causing the indexer to discover and process thousands of irrelevant files from `node_modules`. Always use `{pattern1,pattern2}` inside the glob string.
